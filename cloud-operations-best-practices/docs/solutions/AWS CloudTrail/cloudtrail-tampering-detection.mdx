# Real-Time CloudTrail Tampering Detection and Automated Remediation

AWS CloudTrail is the foundation of your AWS audit trail. Protecting its integrity is critical — if logging is stopped or the trail is deleted, you lose visibility into account activity at exactly the moment you may need it most.

This solution deploys a layered detection and response stack that alerts your security team within seconds of a CloudTrail tampering event and, optionally, automatically re-enables logging without human intervention.

## How This Solution Works Alongside AWS Config

This solution and AWS Config are complementary layers — AWS Config provides periodic compliance evaluation and configuration history, while this solution adds near real-time event-driven alerting (~30 seconds via EventBridge) and automated response. Deploying both maximizes your security posture.

:::note Defense-in-Depth
AWS Config gives you compliance history and drift detection; this solution gives you near real-time alerting and automated response. Neither replaces the other.
:::

## Detection Architecture

Two parallel detection paths both route to the same Amazon SNS topic:

| Layer | Mechanism | Latency |
|---|---|---|
| EventBridge rules | Direct API event matching | ~30 seconds |
| CloudWatch metric filters + alarms | Log-based detection | 1–5 minutes |

![CloudTrail Security Monitoring Architecture](/img/solutions/cloudtrail-security-monitoring/architecture-diagram.svg)

**EventBridge rules deployed:**
- **Trail tampering rule** — matches `StopLogging`, `DeleteTrail`, `UpdateTrail` from `aws.cloudtrail`
- **S3 bucket protection rule** — matches `DeleteBucket`, `DeleteBucketPolicy`, `PutBucketAcl` from `aws.s3`

**CloudWatch metric filters deployed:**

| Event | Metric | Namespace |
|---|---|---|
| `StopLogging` | `StopLoggingCount` | `CloudTrailSecurityMonitoring` |
| `DeleteTrail` | `DeleteTrailCount` | `CloudTrailSecurityMonitoring` |
| `UpdateTrail` | `UpdateTrailCount` | `CloudTrailSecurityMonitoring` |

**Optional Lambda Auto-Remediation:** When `EnableAutoRemediation=true`, a Lambda function automatically calls `cloudtrail:StartLogging` when a `StopLogging` event fires. The IAM execution role is scoped to the specific trail ARN only.

## Multi-Region and Organization-Level Deployment

CloudTrail and EventBridge rules are regional. To protect all regions, deploy this stack in each region using **CloudFormation StackSets** with AWS Organizations integration for automatic coverage of new accounts.

For organization-level prevention (not just detection), combine this solution with:
- An **AWS Organizations trail** — member accounts cannot delete an organizational trail
- An **SCP** to deny `StopLogging`/`DeleteTrail` across all accounts (see [Strengthening Trail Deletion Prevention](#strengthening-trail-deletion-prevention))

## Prerequisites

Before deploying, verify the following:

- **Active CloudTrail trail** with CloudWatch Logs integration enabled. Note the log group name.
- **SNS email confirmation** — click the confirmation link after stack creation.
- **IAM permissions** — `CAPABILITY_IAM` and `CAPABILITY_NAMED_IAM` required.
- **S3 bucket security** — Block Public Access, SSE encryption, versioning, and access logging must be configured on the CloudTrail log bucket.
- **CloudWatch Logs encryption** — the log group must be encrypted with a customer-managed AWS KMS key:
  ```bash
  aws logs associate-kms-key --log-group-name <log-group> --kms-key-id <key-arn>
  ```

:::warning Template Does Not Validate S3 Prerequisites
The CloudFormation template does NOT validate S3 bucket security settings. The stack deploys successfully even if prerequisites are not met. Run `./scripts/validate-prerequisites.sh <bucket> <log-group>` before deploying — it blocks deployment if any requirement is not met.
:::

For continuous enforcement after deployment, enable these AWS Config managed rules:
- `s3-bucket-public-read-prohibited`
- `s3-bucket-server-side-encryption-enabled`
- `s3-bucket-versioning-enabled`
- `s3-bucket-logging-enabled`

## Deployment

### Download the Template

[`cloudtrail-security-monitoring.yaml`](../../../static/cfn-templates/cloudtrail-security-monitoring/cloudtrail-security-monitoring.yaml)

### Parameters

| Parameter | Default | Description |
|---|---|---|
| `CloudTrailLogGroupName` | *(required)* | CloudWatch Logs log group receiving CloudTrail events |
| `NotificationEmail` | *(required)* | Email address for SNS alert notifications |
| `TrailName` | *(required)* | Name of the CloudTrail trail to protect |
| `EnableAutoRemediation` | `false` | Deploy Lambda to auto re-enable stopped trails |
| `CloudTrailLogBucketName` | *(optional)* | S3 bucket for CloudTrail logs — applies hardening policy when provided |

### Implementation Priority

1. Verify S3 bucket and CloudWatch Logs prerequisites
2. Deploy detection-only stack (`EnableAutoRemediation=false`) and confirm SNS subscription
3. Validate alerting — trigger a test `StopLogging` event and confirm alert arrives
4. Provide `CloudTrailLogBucketName` to apply S3 hardening policy
5. Enable auto-remediation (`EnableAutoRemediation=true`)
6. Attach `MonitoringStackProtectionPolicy` to IAM roles; apply SCP if using AWS Organizations
7. Use CloudFormation StackSets for multi-region rollout

:::tip EnableAutoRemediation
When enabled, the Lambda function calls `cloudtrail:StartLogging` automatically on `StopLogging` events, minimizing the window during which logging is inactive. The IAM role is scoped to the specific trail ARN only.
:::

## Incident Response Playbook

| Event | Immediate Action |
|---|---|
| `StopLogging` | Verify auto-remediation fired (check Lambda logs). If not, manually re-enable. Investigate the principal. |
| `DeleteTrail` | Cannot be auto-restored. Recreate the trail immediately. Investigate the principal. |
| `UpdateTrail` | Review the change — check for disabled log validation, changed S3 destination, or removed CloudWatch Logs integration. |
| S3 bucket events | Verify log delivery is intact. Restore bucket policy if needed. |

**For all events:** Revoke credentials if unauthorized. Restore configuration from IaC baseline. Review IAM policies to understand how the principal obtained permissions.

## Strengthening Trail Deletion Prevention

Trail deletion cannot be automatically reversed. Apply these additional controls:

### Option 1: AWS Service Control Policy (Recommended for AWS Organizations)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyCloudTrailDeletion",
    "Effect": "Deny",
    "Action": ["cloudtrail:DeleteTrail","cloudtrail:StopLogging","cloudtrail:UpdateTrail"],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:PrincipalArn": ["arn:aws:iam::<ACCOUNT_ID>:role/BreakGlassRole"]
      }
    }
  }]
}
```

:::note Break-Glass Role
Tightly control the break-glass role: no standing access, MFA required for assumption, all usage logged and alerted.
:::

### Option 2: IAM Permission Boundary (Standalone Accounts)

```json
{
  "Version": "2012-10-17",
  "Statement": [{"Sid": "DenyTrailDeletion","Effect": "Deny","Action": "cloudtrail:DeleteTrail","Resource": "*"}]
}
```

### Option 3: AWS Organizations Trail

Member accounts cannot delete an organizational trail — only the management account has that permission. This provides architectural prevention.

### Option 4: AWS Config Automated Remediation

Enable the `cloudtrail-enabled` AWS Config managed rule with an AWS Systems Manager Automation runbook to recreate a deleted trail automatically.

:::tip Recommended Combination
Combine **Option 1 (SCP)** with **Option 3 (Organizations trail)** for the strongest posture.
:::

## Data Security and Classification

**Data classification:** CONFIDENTIAL — the SNS topic receives CloudTrail event details including IAM principal ARNs, source IP addresses, and API call parameters.

### Encryption

| Resource | Encryption |
|---|---|
| Amazon SNS topic | Customer-managed AWS KMS key with automatic annual rotation |
| Amazon SQS Dead Letter Queue | Same AWS KMS key as SNS topic |
| CloudWatch Logs | Customer-managed AWS KMS key (customer responsibility — configure before deployment) |
| Data in transit | TLS enforced via S3 bucket policy (`aws:SecureTransport: false` deny) |

### AWS KMS Key Management Strategy

- **Key rotation** — Automatic annual rotation enabled (`EnableKeyRotation: true`)
- **Key policy** — Scoped to Amazon SNS, Amazon CloudWatch, Amazon EventBridge, CloudWatch Logs, and account root via `kms:ViaService` conditions
- **Key alias** — `alias/cloudtrail-monitoring-sns-<stack-name>`
- **Deletion policy** — `DeletionPolicy: Retain` — minimum 7-day waiting period before deletion

> **BYOK Review Required:** Security team must review and approve AWS KMS key policy grants before production deployment.

### Retention

| Resource | Retention |
|---|---|
| CloudWatch Logs | 90 days minimum, 365 days recommended. Set with: `aws logs put-retention-policy --log-group-name <name> --retention-in-days 365` |
| Amazon SQS DLQ | 14 days (configured in template) |
| Amazon SNS | Not retained after delivery |

## Security Considerations

### Auto-Remediation Risks

- **False positives** — Legitimate `StopLogging` calls (e.g., maintenance) will be reversed automatically. Scope to a specific trail using the `TrailName` parameter.
- **Remediation loop** — Repeated `StopLogging` attacks trigger repeated Lambda invocations. Monitor the DLQ alarm.
- **IAM scope** — `cloudtrail:StartLogging` is scoped to the specific trail ARN only.

### IAM Access Reviews

| Frequency | Action |
|---|---|
| Quarterly | Review Lambda execution role and protection policy attachments. Use IAM Access Analyzer. |
| Annually | Audit principals with `cloudformation:UpdateStack` or `DeleteStack` on this stack. |
| On team changes | Revoke Amazon SNS subscriptions and stack modification permissions. |
| Continuously | Review CloudTrail logs for IAM policy usage patterns. |

### Residual Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Trail deletion cannot be auto-reversed | High | Apply SCP or Organizations trail |
| Multi-region gaps | Medium | Deploy stack in every region with active trails |
| CloudWatch Logs delivery delay | Low | EventBridge layer provides ~30-second detection |
| Lambda DLQ not monitored | Medium | CloudWatch alarm on DLQ message count is deployed |
| AWS KMS key deletion | High | `DeletionPolicy: Retain` — schedule deletion only after confirming no active use |
| MFA Delete not enabled | Medium | Requires root credentials — enable manually after deployment |

This solution adds near real-time detection and automated response to your CloudTrail security posture.
